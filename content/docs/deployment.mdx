## Production build

```md
pnpm build
```

This runs `packages/content`'s build (which in turn builds `packages/validation` first) and
then `next build` in `apps/web`. Every template page is statically generated at build time
(`generateStaticParams` in `apps/web/app/templates/[provider]/[category]/[slug]/page.tsx`) —
there's no database or API call at request time for template content.

## Self-hosting with Node.js

```md
pnpm build
pnpm --filter web start
```

`pnpm --filter web start` runs `next start`, serving the build from `apps/web/.next`. Put a
reverse proxy (nginx, Caddy) in front of it for TLS in production; no other runtime
dependency is required — no database, no external API keys, no accounts to provision (see
architecture.md §1's zero-SaaS-core constraint).

## Deploying to Vercel

This is a standard Next.js app inside a pnpm monorepo, which Vercel supports natively:

1. Import the repository in Vercel.
2. Set the **Root Directory** to `apps/web`.
3. Vercel auto-detects the framework (Next.js) and package manager (pnpm) from the lockfile.
4. Override the **Build Command** to make sure the content pipeline runs first:

   ```md
   cd ../.. && pnpm --filter @ai-template/content run build && cd apps/web && pnpm exec next build
   ```

   (Or simpler: set the build command to `pnpm run build` at the **repo root**, with the
   Vercel project's Root Directory left at the repository root and Output Directory set to
   `apps/web/.next` — either approach works; the key requirement is that
   `@ai-template/content`'s build step runs before `next build`.)

No environment variables are required for the core product to run.

## Deploying to GitHub Pages

GitHub Pages has no server, so this target builds a fully static export instead of the default
server build. `.github/workflows/deploy-pages.yml` does this automatically on every push to
`main`:

1. It sets `GITHUB_PAGES=true`, which switches `apps/web/next.config.ts` to
   `output: "export"` and adds the `basePath`/`assetPrefix` needed for a project site served
   from `https://<owner>.github.io/AI-TEMPLATE/` (a subpath, not the domain root).
2. It sets `NEXT_PUBLIC_SITE_URL` from `actions/configure-pages`' detected origin and base path,
   so the sitemap, RSS feed, canonical URLs, and OG images resolve to the real GitHub Pages URL.
3. It uploads `apps/web/out` (the static export) and publishes it with `actions/deploy-pages`.

**One-time manual step** (the workflow can't do this on its own): in the repository's
**Settings → Pages → Build and deployment**, set **Source** to **GitHub Actions**. Once that's
set, every push to `main` redeploys the site.

To build the same export locally:

```md
GITHUB_PAGES=true NEXT_PUBLIC_SITE_URL=https://<owner>.github.io/AI-TEMPLATE pnpm --filter web build
```

The static export is written to `apps/web/out/`. A few static-export constraints this app
already accounts for, in case you extend it:

- Route Handlers and file-convention metadata routes (`sitemap.ts`, `robots.ts`, `feed.xml`,
  `opengraph-image.tsx`, etc.) each need an explicit `export const dynamic = "force-static";` —
  Next won't include them in a static export otherwise.
- Pages that read search params must do it client-side with `useSearchParams()` (see
  `features/templates/compare-view.tsx`), since static export has no server to read a request's
  query string from.
- Plain `<a>` tags, not `next/link`, are used for links to Route Handlers like `/feed.xml` —
  `Link` tries to RSC-prefetch its target as if it were a page, which 404s against a Route
  Handler. The favicon and apple-touch-icon are served from explicit routes
  (`app/favicon.png/route.tsx`, `app/apple-touch-icon.png/route.tsx`) and referenced via
  `metadata.icons` in `app/layout.tsx` for the same reason — Next's auto-generated favicon
  `<link>` from the `icon`/`apple-icon` file convention isn't `basePath`-prefixed under
  `output: "export"`.

## Optional: NEXT_PUBLIC_SITE_URL

Set this to your real production origin (e.g. `https://your-domain.com`) so the sitemap, RSS
feed, canonical URLs, and generated OpenGraph images resolve to absolute URLs that match where
the site is actually deployed, instead of the `https://ai-template.dev` placeholder in
`apps/web/lib/site.ts`. Nothing breaks without it — search engines and social crawlers just see
the placeholder domain in metadata until it's set.

## What's not wired up yet

Analytics, authentication, and community features are reserved interfaces
(`AuthProvider`, `AnalyticsSink` in architecture.md §7), not implemented — there is nothing to
configure for them because they don't exist yet. When they land, this page will document the
environment variables they add; until then, a deploy needs zero secrets.
